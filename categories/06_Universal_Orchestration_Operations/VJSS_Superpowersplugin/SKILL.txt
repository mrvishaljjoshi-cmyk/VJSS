# Superpowers (Claude Code Plugin) — Notes

Source: YouTube walkthrough by Alex, Grit AI Studio. Plugin created by Jesse Vincent ("Obra" on GitHub).

## Credits
- **Video walkthrough**: Alex, [Grit AI Studio](https://www.youtube.com/@GritAIStudio) on YouTube — these notes are a summary of that video; watch it there for the full context and demo.
- **Plugin**: Superpowers by Jesse Vincent ("Obra" on GitHub).

## What it is
A structured workflow plugin for Claude Code that enforces: **explore → plan → code**, matching Anthropic's own best-practice advice, but automated and gated rather than optional. Core philosophy: invest heavily in brainstorming/planning up front so implementation can be near one-shot.

## Install
Superpowers ships in the official Anthropic Marketplace (already registered when Claude Code is installed) — no need to add a marketplace first.

```
/plugin
```
Then select/install Superpowers from the list. Verify install via the plugin/install tab — should show 14 skills and 3 key commands.

Note: unlike some community plugins, no separate `/plugin marketplace add ...` step is needed — Superpowers lives in the official Anthropic Marketplace, which is registered by default.

## Three core commands
Typed directly into a Claude Code session once the plugin is installed:

```
brainstorm
```
Starts phase 1 — Claude explores the project and begins the question-by-question design discussion.

```
write plan
```
Generates the implementation plan (file inventories, verification commands, success criteria, rollback steps) from an approved brainstorm/spec.

```
execute plan
```
Runs the plan via sub-agent dispatch, batched with review checkpoints.

## The 7-phase workflow
1. **Brainstorming** — Claude explores the project context, asks one question at a time, presents the design in sections for approval. Offers a browser-based visual companion for anything UI/layout/architecture related. Hard gate: no code until design is approved.
2. **Git worktree isolation** — creates an isolated worktree before touching code; main branch stays clean, easy to discard if things go wrong. Handled automatically by the skill; no manual `git worktree` commands needed from you.
3. **Planning** — breaks work into granular tasks: file inventories, verification commands, success criteria, rollback procedures. Written to be followable by "an inexperienced engineer with no context," per the project's own framing.
4. **Sub-agent-driven development** — dispatch tasks to parallel sub-agents in the current session, or hand the plan to a fresh session for a clean context window.
5. **Test-driven development** — the "iron law": no production code without a failing test first (red → green → refactor).
6. **Code review** — each sub-agent's work is reviewed against spec before issues compound.
7. **Branch completion** — merge decision, cleanup, PR creation if needed.

Note: phases 2 and 5–7 (worktree setup, running tests, verification commands, merge/PR) are executed by Claude itself as part of the skill — you don't type these commands manually, but Claude will show you the actual shell/git/test commands it runs as it goes.

Skills trigger automatically based on context — not invoked manually.

## The 14 skills (by category)

**Core workflow**
- Brainstorming (hard gate + visual companion)
- Writing plan (implementation roadmap generator)
- Executing plan (batches with review checkpoints)

**Development**
- Test-driven development
- Systematic debugging (four-phase root cause analysis, no guessing)
- Sub-agent-driven development (parallel dispatch + spec review)

**Quality assurance**
- Requesting code review (launches review sub-agent)
- Receiving code review (handles feedback — explicitly told to verify technically rather than blindly agree)
- Verification before completion (must run and confirm verification commands before claiming success — "evidence before assertions")

**Operations**
- Using git worktree (isolated dev branches)
- Finishing a development branch (merge/PR/cleanup decision tree)
- Dispatching parallel agents (multi-agent coordination)

**Meta**
- Writing skills (TDD-style rigor applied to creating new skills)
- Using superpowers (ties the whole framework together)

## Visual companion (brainstorming feature)
- Triggers automatically when brainstorming touches UI layouts, components, architecture diagrams, or navigation structures.
- Spins up a local browser-based server; Claude writes HTML content fragments, the server wraps them in a styled, interactive frame.
- Built-in UI primitives: clickable A/B/C option cards, comparison cards, wireframe "mockup" containers, split/side-by-side views, pro/con layouts, mock nav/sidebar/button/input elements.
- User clicks are logged to an events file; Claude reads both the click data and follow-up text feedback (click-tracking can be inconsistent — typing your choice is a reliable fallback).
- Mockups persist in a `superpowers/brainstorm` folder in the project directory (can be gitignored).
- Server auto-exits after 30 minutes of inactivity.
- Useful beyond coding: presentation structure, content strategy, information architecture — anywhere side-by-side visual options beat text description.

## Spec review loop
After brainstorming approval, Superpowers writes a design spec to `Docs/Superpowers` and commits it to git, then:
- Dispatches a spec-reviewer sub-agent to check for issues/ambiguities/gaps.
- Claude fixes issues, reviewer re-runs — up to 5 iterations before escalating to the user.
- After automated review passes, the user reviews and approves the spec.
- Only then does implementation planning begin.

## Pro tips (from the video)
- Don't rush past brainstorming — the time spent there pays off in fewer rework cycles later.
- Say yes to the visual companion for any UI-related work.
- Actually read the generated plan document before execution starts.
- Treat the verification step as non-negotiable — don't let completion claims go unchecked.
- Try both execution modes: sub-agents in the current session for smaller tasks, fresh session for larger ones.
- Test it on a real task, not a toy example, to see the actual benefit.

## Writing good prompts for Superpowers

The plugin's Q&A loop does a lot of the specification work for you — so the goal of your *first* message isn't to write a perfect spec, it's to give Claude enough to ask good questions. Under-specifying is recoverable (it'll ask); over-specifying rigid solutions up front can crowd out better designs it would otherwise propose.

**Kicking off `brainstorm`**
Structure the opening prompt around four things, roughly in this order:
1. **Goal** — the outcome, not the implementation. ("Users should be able to export their data as CSV" not "add a `toCsv()` method to the Export class.")
2. **Constraints** — performance limits, backward compatibility, deadlines, tech already chosen, things that must NOT change.
3. **Context** — relevant files, existing patterns to follow/avoid, prior art elsewhere in the codebase.
4. **Explicit non-goals** — what's out of scope for this pass, so brainstorming doesn't sprawl.

```
brainstorm

Goal: let users export a saved report as PDF, not just CSV.
Constraints: must reuse the existing report-rendering pipeline in
src/reports/, no new external PDF service (cost), needs to work for
reports with >10k rows without blocking the request thread.
Context: CSV export already exists at src/reports/exportCsv.ts —
PDF should follow a similar entry-point shape.
Out of scope: email delivery of the PDF, scheduling recurring exports.
```

Weak version to avoid: `brainstorm — add PDF export`. It's not wrong, just slow — every constraint above becomes a round-trip question instead of being answered up front.

**During the question loop**
- Answer the actual question asked before adding extra info — tangents get lost if the loop moves on before Claude captures them.
- "Not sure, you decide" is a legitimate answer — the gate won't advance past an unresolved ambiguity, so it's safe to punt on things you truly don't have an opinion on.
- Correct wrong assumptions immediately and explicitly ("no — reuse the existing auth middleware, don't write a new one") rather than letting it ride into the plan.
- If the visual companion pops an option grid, clicking is fine but typing your reasoning ("B, but only if it doesn't require a schema migration") gives Claude more to work with than the click alone.

**`write plan`**
Usually needs no extra prompt — it consumes the already-approved spec. Add a prompt only to steer scope or sequencing that the spec left open:
```
write plan — backend and API only for this pass; the frontend
consumer is a separate follow-up plan.
```

**`execute plan`**
Same idea — bare `execute plan` is normal. Worth adding a line when you have a preference on execution mode or checkpoint cadence:
```
execute plan — run in the current session, pause for my review
after each top-level task rather than batching them.
```

**General habits that carry over from prompting Claude Code elsewhere**
- State the "why" behind a constraint, not just the constraint — it lets Claude trade off correctly when two of your requirements conflict (e.g., "must not block the request thread *because* reports can hit 10k+ rows" is more useful than the bare constraint).
- Reference concrete files/functions by path when you already know the relevant code — saves an exploration round-trip in phase 1.
- If a past brainstorm/plan in this project set a convention you want followed again, say so explicitly; Superpowers doesn't carry memory of prior sessions on its own.

## Bottom line
Superpowers turns Claude Code into a more methodical partner: structured brainstorming, enforced TDD, self-review, and evidence-based completion claims — automating the explore/plan/execute loop Anthropic already recommends doing manually.
